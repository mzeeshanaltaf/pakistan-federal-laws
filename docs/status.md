## Phase 2 — Ingest Pass A (done)

`ingest/` (Python, run against the live VPS Postgres from a local machine — `docs/laws/` isn't reachable from the VPS): `common.py` (env/DB/slug helpers), `01_catalogue.py`, `02_chunk_embed.py`, `03_build_indexes.py`, `requirements.txt`.

- **01_catalogue.py** — upserted all 525 `status: "ok"` records into `categories` (21) and `documents`. Category is derived from the on-disk folder (`abs_path.parent.name`), not the `category` string field, per the `docs/`/`docs/laws/` and `/`-vs-`-` gotchas in `CLAUDE.md`/`00-overview.md` — verified 1:1 folder↔(category,catid) mapping and zero missing files before running for real. `instrument_type`/`enacted_year` parsed from the title by regex; 1 title has no instrument type ("Code of Civil Procedure (CPC), 1908 (Under Review)") and 2 have no parseable year (one is a bare title, one has a typo'd year `I962`) — left `NULL`, both columns are nullable. Re-running is idempotent: `ingest_status` only resets to `pending` when a document's checksum actually changed (`IS DISTINCT FROM` in the `ON CONFLICT` update), so a stable re-run doesn't reprocess everything downstream.
- **02_chunk_embed.py** — per-page extraction via PyMuPDF, strips the `Page N of M` header, splits on blank-line paragraph boundaries, collapses internal whitespace. Chunks at ~250 tiktoken tokens (`cl100k_base`) with 50-token (20%) overlap, never merging across a page gap >1 (segments the paragraph stream first, chunks each segment independently). `section_ref` captured when a chunk's content itself opens on a `^\d+[A-Z]?\.\s+[A-Z]` heading. **Deviation from the plan doc, decided mid-phase with the user:** the plan originally specified ~900 tokens/150 overlap. That's large relative to standard RAG practice (typical dense-retrieval defaults are 256–512 tokens with 10–20% overlap — LangChain's default splitter lands around 250 tokens/20%) and would have meant ~3,600 tokens of grounding context per a 4-chunk retrieval. Revised down to **250/50 (20%)**, with Phase 4 compensating by retrieving 6–8 chunks instead of 4 — smaller, more topically-focused chunks give sharper vector similarity (re-running the same test query after the revision raised top-hit cosine similarity from ~0.55 to ~0.65) while keeping total retrieved context comparable. **Note for Phase 4:** [phase-4-retrieval-chat-ui.md](plan/phase-4-retrieval-chat-ui.md) still says "keep top 10, cap context at ~6k tokens" from before this revision — reconcile with the 6–8/250-token decision when that phase starts.
  - Also added a bounded fallback (sentence-boundary split, then hard token-slice as a last resort) for the small fraction of paragraph blocks that are themselves oversized — this corpus's PDFs don't always have blank-line gaps between clauses (confirmed by inspection), so without the fallback a few chunks would be unboundedly large. Never a correctness problem either way (`text-embedding-3-small`'s limit is 8,191 tokens), just a chunk-quality note.
  - Embeddings batched 100 chunks/request with exponential backoff on `RateLimitError`/`InternalServerError`/`APIConnectionError`/`APITimeoutError`. Each document's delete+insert+status-update is one DB transaction (atomic per document, resumable — a failure leaves `ingest_status` alone for retry rather than a partial write). One `usage_events` row per embedding batch, costed from `model_pricing`.
- **03_build_indexes.py** — builds the HNSW index (`db/create-vector-index.sql`), re-asserts the GIN index, `ANALYZE`s both tables, refreshes `categories.document_count` (counts only `ingest_status='chunked'` documents per category). Re-run after the 250/50 re-chunk — the HNSW index was dropped first (`DROP INDEX`) rather than left to incrementally absorb a full-table delete+reinsert, per the plan doc's own "build after bulk insert, not incrementally" guidance.
- **Result (final, at 250/50):** all 525 documents `ingest_status='chunked'`, **0 failures** across both the initial 900/150 run and the 250/50 re-chunk. **23,176 chunks** live in `document_chunks` (plan doc's revised estimate: ~23k), **6,301,820 tokens** billed for the 250/50 run (**$0.126**). `usage_events` is a cost ledger, so it correctly retains both runs' entries — cumulative logged ingest spend across the two chunking attempts is **$0.232** (1,146 events, 11,612,928 tokens); the 900/150 chunks and their cost are gone from `document_chunks` (deleted and replaced) but the money already spent on that first pass is still true history, not deleted from the ledger. Re-verified retrieval after the switch with the same real query (`ORDER BY embedding <=> query_vec`) against the Arms Act corpus — top-8 chunks were tightly on-topic (penalty/license sections) at higher similarity than the 900-token version, totaling ~1,700 tokens for 8 chunks vs. ~3,600+ for 4 chunks previously.
- The pre-existing Postgres collation-version warning (`database was created using collation version 2.41... provides version 2.36`) surfaces on every connection — harmless, pre-dates this phase, VPS-level, not fixed here.

## Phase 3 — Ingest Pass B (done)

`ingest/04a_export_extracts.py`, `ingest/04b_load_summaries.py`, and `ingest/05_category_questions.py` all built and run to completion.

- **04a_export_extracts.py** — per-document extract exporter, matching the plan's ≤6,000-token full-text / else CONTENTS+preamble+sections 1-3+body-head+body-tail budgeting. Region-finding (CONTENTS block, preamble, sections 1-3) is regex-heuristic over the corpus's documented conventions (`CLAUDE.md`: 98% CONTENTS block, 85% WHEREAS preamble) — not exact, but sufficient as authoring aid since I (Claude) read the extract directly rather than parsing it programmatically. Selects documents with `ingest_status='chunked'`; supports `--category`, `--only` (comma-separated slugs), `--limit`, `--force` (also allows already-`summarized` docs, for re-export). Writes `ingest/out/extracts/<slug>.txt` and `ingest/out/manifest.jsonl` (both gitignored, already covered by the existing `ingest/out/` rule).
- **04b_load_summaries.py** — reads a summaries JSONL file, validates each record (non-empty `summary`/`summary_short` strings, non-empty `key_topics`/`questions` string lists), upserts into `documents.summary*`/`key_topics`, sets `summary_author='claude'`, `summary_model='claude-sonnet-5'`, `summarized_at`, `ingest_status='summarized'`; replaces that document's `scope='document'` `suggested_questions`; logs one `usage_events` row per document (`provider='anthropic'`, `operation='summary'`, `is_estimated=true`, input tokens from the manifest's extract token count, output tokens counted via `tiktoken` over the written summary text — not billed API usage, since no API call is made in this phase).
- **05_category_questions.py** — reads `ingest/out/category_questions.jsonl` (21 records, one per category: `blurb` + 3 `questions`, authored by me reading each category's document titles/summaries), validates, upserts `categories.blurb`, replaces that category's `scope='category'` `suggested_questions`.
- **Trial run** (2 documents, `Asian Development Bank Ordinance, 1971` and `Bankers' Books Evidence Act, 1891`) reviewed and approved by the user before scaling up.
- **Full run:** exported extracts for the remaining 523 documents via `04a` (no `--limit`), then authored summaries at scale by **fanning out 32 parallel background subagents**, each assigned a ~50k-token budget-packed batch (bin-packed from `ingest/out/manifest.jsonl`, largest-first greedy packing) of 5–66 documents, writing to its own `ingest/out/batches/batch_NN.jsonl` to avoid write contention. This deviates from the plan doc's literal "I read extracts in budget-packed batches ... and append to summaries.jsonl" — parallelized across subagents rather than done serially by the main session, for wall-clock efficiency at this scale. Each subagent followed the same style rules (plain language, name specific sections, flag old/amended acts, never assert an unstated penalty/fee/period) and the same JSON schema.
  - Hit real-world friction requiring retries: the harness's 20-concurrent-subagent cap blocked ~8 batches on first launch (relaunched as slots freed); one batch (30, the largest at 66 docs) was twice interrupted mid-run by a Claude Code monthly spend-limit error and once left silently truncated at 40/66 docs — resolved by diffing each batch file's slugs against its expected list from `batches.json`, then relaunching only the missing/corrupted slugs (a `batch_30b.jsonl` for the 26 stragglers, later merged in). A user-initiated interrupt (likely a "kill all agents" action) also killed several in-flight batches with no output — recovered the same way, by validating actual file state and relaunching only what was actually missing, never trusting agent self-reports alone.
  - **Final merge validated all 32 batches (+ `batch_30b`) against `batches.json`'s expected slug lists before loading — 523/523 slugs present, 0 corrupted, 0 duplicates.** Merged into `ingest/out/summaries.jsonl` alongside the 2 trial records (525 total, matching the full `status:"ok"` corpus), then ran `04b_load_summaries.py` once over all 525 (idempotent per-slug upsert, so re-processing the 2 already-loaded trial docs was harmless — see cost note below).
  - Authored `ingest/out/category_questions.jsonl` by hand (21 categories, reading each category's document title list) and ran `05_category_questions.py`.
- **Result:** all **525/525** documents `ingest_status='summarized'`, 0 failures, 0 skipped. **1,575** document-scope `suggested_questions` (525 × 3) + **63** category-scope (21 × 3). All 21 `categories.blurb` populated. Total authoring cost per `usage_events` (`operation='summary'`, `provider='anthropic'`, `model='claude-sonnet-5'`, `is_estimated=true`): **527 events** (525 unique documents + 2 duplicate entries from the trial docs being re-processed in the full `04b` run — harmless double-counting in the cost ledger, consistent with Phase 2's "ledger retains true history" precedent), **~1.56M input / ~296K output tokens**, **≈$6.08** total.
- **Fixed a latent bug found during this phase:** `ingest/03_build_indexes.py`'s `categories.document_count` refresh only counted `ingest_status='chunked'` documents — once Phase 3 moved everything to `'summarized'`, a re-run would have zeroed every category's count. Widened the WHERE clause to `IN ('chunked', 'summarized')` (both the `UPDATE` and the summary print), then re-ran `03_build_indexes.py` to rebuild the HNSW/GIN indexes and refresh counts — `sum(categories.document_count) = 525`, confirmed correct.
- Scratch files from the batch-authoring process (`ingest/out/batches/`, `batches.json`, `batch30_missing.json`, `category_data.json`, `category_titles.json`, `summaries_merged.jsonl`) are left on disk under `ingest/out/` (already gitignored) rather than cleaned up — harmless, and useful if the summaries ever need re-auditing against their source batches.

**Backend (`src/lib/`):**
- `db.ts` — pg `Pool` singleton, `search_path=pak_laws,public`. **Deviation found during testing:** `db/schema.sql` never schema-qualified `CREATE EXTENSION vector`, so the `vector` type lives in `public` — `search_path=pak_laws` alone (no `public`) makes every `::vector` cast fail with `type "vector" does not exist`. Also caps `max: 4` per Pool — static-generating the 525 `/law` pages runs 18 parallel build-worker processes, each with its own Pool (the `globalThis` cache only helps within one process); the default pool size across 18 workers exhausted the shared VPS Postgres's connection limit (`sorry, too many clients already`) partway through the first full build.
- `storage.ts`, `usage.ts`, `rate-limit.ts`, `retrieval.ts` (hybrid RRF search), `intent.ts`, `rag-prompt.ts`, `chat-types.ts`, `catalog.ts`, `anon-id.ts` — built per the plan. `retrieval.ts`/`rag-prompt.ts`'s `Citation` shape grew a `sourceUrl` field (joins `documents.source_url`) beyond what the phase doc's citation description implied, needed for the reference panel's "View on pakistancode.gov.pk" link called for in the same phase doc's UI section.
- **RRF/context-cap reconciliation** (flagged as open in Phase 2's notes): top **8** fused chunks, context capped at **~3,000 tokens**, superseding the phase doc's pre-rechunk "top 10 / ~6k tokens" language.
- **Real bug caught by testing, not inspection:** the phase doc's summary-intent regex (`/\b(summar|overview|...)\b/i`) never actually matches "summary"/"summarize" — the trailing `\b` can't match between "summar" and "y" (no word boundary between two word characters), so the literal regex silently never fires. Fixed in `intent.ts` with `summar\w*`.
- `suggestions` route's `scope=all`: the schema only has `document`/`category`-scoped `suggested_questions` rows (no `all`), so unscoped suggestions sample 6 random `category`-scoped questions.

**API routes (`src/app/api/`):** `chat`, `catalog`, `suggestions`, `documents/[slug]/summary`, `documents/[slug]/file`, `chat/history` — all built and curl-verified against real data. `chat/route.ts` built with the `ai-sdk` skill consulted live against the *installed* package versions (`ai@7.0.77`, `@ai-sdk/openai@4.0.46`) rather than from memory — caught real version-specific facts: `onFinish` → `onEnd`, `openai(modelId, settings)`'s two-arg form isn't in this installed provider version (uses `providerOptions.openai.reasoningEffort` instead), and `LanguageModelUsage`'s current field names (`inputTokenDetails.cacheReadTokens`, `outputTokenDetails.reasoningTokens`).
- **Real stream-protocol bug found via browser testing, not visible in curl:** writing the `data-citations`/`data-source` parts before `streamText`'s merged stream (which emits its own implicit `start`) produced **two** separate assistant messages client-side instead of one — the data parts got treated as their own message, and the merged stream's `start` began a second. Fixed by writing an explicit `{type: "start"}` first and passing `sendStart: false` to `toUIMessageStream`.
- **Real citation-rendering bug also only visible in-browser:** `react-markdown`'s URL sanitizer silently strips custom URI schemes (`qanoon-citation:5` → `href=""`) as an XSS precaution, so citation pills rendered as dead plain-text numbers. Fixed by using a `#qanoon-citation-5` fragment href instead (fragments are always allowed through).

**UI, via `impeccable`:** register is `product` by default (`/` overrides to `brand` per-surface, per the phase doc's own framing). ## Phase 12 — User dashboard (done)

Built per the plan doc: `src/lib/dashboard-queries.ts` (`getDashboardStats`, `getBookmarkedMessages`), `src/app/dashboard/page.tsx` rewritten from Phase 10's placeholder into real stat tiles + a bookmarks list, and the bookmark deep-link back into `/ask` (`src/app/ask/page.tsx` → `ask-app-loader.tsx` → `ask-app.tsx` → `chat-thread.tsx`'s `useRestoredSession`).

- **Real bug found and fixed — the plan doc's own totals SQL double-counts.** Its query `LEFT JOIN`s both `chat_messages` and `usage_events` directly onto `chat_sessions` in the same `SELECT`. Postgres cross-products the two joins per session (every message row × every usage-event row for that session), so `count(*) FILTER (WHERE cm.role = 'user')` and `SUM(ue.total_tokens)` both get inflated by a multiplicative factor once a session has more than one of each — which is virtually always, since every chat turn logs at least a `query_embedding` and a `chat` event. Caught via a live test: 3 real questions across 2 sessions came back as `questions_asked = 10` with the literal plan SQL. Fixed in `getDashboardStats` by pre-aggregating `chat_messages` and `usage_events` into per-`session_id` subqueries *before* joining to `chat_sessions`, then summing those already-correct per-session values — re-verified against a manual `usage_events` sum for the same test user (8,544 tokens, matching exactly) and against the plan's own verification instruction ("totals match manual counts").
- **Second real bug found and fixed — bookmark labels.** `chat_sessions.title` is essentially never populated by the existing chat flow (confirmed: null on every session in this test), so using it as the bookmark list's display label per a literal reading of the plan's SQL made every bookmark show "All laws" regardless of actual scope. Fixed by joining `categories`/`documents` on `scope_id` (the same slug `chat-thread.tsx` already uses to build `ChatScope`) in `getBookmarkedMessages`, resolving a real label (category name / document title / "All laws" only when truly unscoped) — exposed as `BookmarkedMessage.label`, used both for on-page display and as the deep link's `label` query param (so the restored `/ask` page shows the correct scope name immediately, not a raw slug).
- Bookmark preview text strips the light markdown (`**bold**`, `[n]` citation markers) assistant answers contain — the dashboard list renders plain text, not full `react-markdown`, so raw asterisks would otherwise leak through.
- **Deep-link scope leak, caught before it shipped:** naively threading `initialSessionId` straight through from `ask-app.tsx` to `ChatThread` on every render meant that if a user landed on a bookmark link and then changed scope via the `ScopeSelector` dropdown, the newly-mounted `ChatThread` (remounted via `key={scopeKey}`) would still receive the *original* deep-linked session id — restoring a different scope's conversation under the newly picked scope. Fixed with a `sessionIdActive` boolean state in `AskApp`, seeded from whether `initialSessionId` was provided and cleared the moment `onScopeChange` fires; `ChatThread` only ever receives `initialSessionId` while it's still true. (An earlier attempt compared `scopeKey` against a `useRef`-captured initial value, but reading `ref.current` during render trips this project's `react-hooks/refs` ESLint rule — replaced with the state-based approach.)
- `useRestoredSession` (`chat-thread.tsx`) now takes an optional `initialSessionId` param: when present, it's used directly (`isNew: false`) instead of `getOrCreateLocalId`, so the existing history/reactions fetch path (already built in Phases 6 and 11) runs unchanged for a deep-linked session — no new fetch logic needed, per the plan doc's framing.
- Stat tiles and the bookmark list reuse this app's existing visual vocabulary (`rounded-xl border border-border` tiles matching `/browse`'s spacing conventions, `divide-y divide-border` list matching `/browse`'s category list) rather than introducing a new `Card` component — none existed in `src/components/ui/` and one wasn't needed for three tiles and a list.
- **Verified live**, not just via build checks — a throwaway Node script drove the real dev server end-to-end with two real signed-in users (same sign-up-then-flip-`emailVerified`-then-sign-in pattern as Phase 11's verification, `Origin` header added to satisfy Better Auth's CSRF check on non-browser requests): user A asked 2 questions in one "all laws" conversation and 1 in a separate "Banking/Financial Laws" conversation (3 real `gpt-5.6-luna` calls), bookmarked the category-scope answer; `getDashboardStats`' fixed query returned `conversations=2, questions_asked=3, total_tokens=8544`, independently cross-checked against a manual `usage_events` sum for that user (exact match); user B (zero activity) correctly returned `conversations=0`. A temporary Playwright install (npm, `--no-save` — `package.json`/`package-lock.json` confirmed clean after, matching Phases 4–11's pattern) then drove an actual browser with user A's real session cookie: `/dashboard` rendered the correct tiles and bookmark ("Banking/Financial Laws", correct content preview, correct date), clicking the bookmark landed on `/ask?sessionId=...&scope=category&slug=banking-financial-laws&label=Banking%2FFinancial+Laws`, and the page restored the exact bookmarked exchange (scope selector showing "Banking/Financial Laws", the original question bubble, the original answer with its citation pill and a still-filled bookmark icon) rather than a fresh session — zero console errors throughout. Both throwaway users deleted afterward (matching Phases 7–11's cleanup precedent).
- `npx tsc --noEmit` and `npm run lint` clean on the app code (the deleted verification scripts triggered only unused-var warnings, not errors, and are gone). `npm run build` (Turbopack, all 572 routes) and `npx next build --webpack` both clean; `/dashboard` renders as a dynamic (`ƒ`) route on both build paths, consistent with `/admin`'s Phase 10 precedent (its auth + DB read runs per-request, not statically).
- **Not verified this phase, needs the user:** the empty-state copy ("Bookmark an answer from a conversation on Ask to save it here.") for a brand-new signed-up user was confirmed correct by code inspection and the `conversations=0` DB check above, but not re-rendered in an actual browser — low risk, it's a static conditional with no new logic.

## Session handoff

Each phase is implemented in a new session with no memory of prior sessions. Before ending a phase:

1. Update the phase checklist above and add or edit that phase's section with what was actually built and any deviations from its plan doc.
2. Leave the changes uncommitted for the user to review. **Do not commit or push automatically** — the user reviews the diff and explicitly asks for commit/push when ready.

A new session starting a phase should: read `CLAUDE.md` (auto-loaded), read this file, read `docs/plan/00-overview.md` and that phase's `docs/plan/phase-N-*.md`, then run `git log --oneline` and `git status` first — uncommitted changes may mean the previous phase's work is still awaiting review, not that it doesn't exist.
